## Краткий рассказ о проекте

В проект собраны четыре решенных задания DevOps: анализатор логов Nginx, проверка доступности сайтов, получение курсов валют и обнаружение изменений страниц. Исходные файлы находятся в `src/`, документация — в `docs/`. История содержит отдельные коммиты для структуры и каждого задания. Дополнительная документация подготовлена в ветке `docs/defense-guide` и предложена к включению в `main` через Pull Request.

## Вопросы преподавателя

| Вопрос | Ответ |
| --- | --- |
| Чем отличаются Git и GitHub? | Git — система контроля версий. GitHub — сервис размещения репозиториев и совместной работы. Git может работать без GitHub и без интернета. |
| Что такое репозиторий? | Файлы проекта вместе с историей и метаданными Git, которые хранятся в `.git`. |
| Чем init отличается от clone? | `init` начинает новый локальный репозиторий. `clone` копирует уже существующий, включая доступную историю и настройку удаленного `origin`. |
| Что делает add? | Помещает текущее содержимое выбранных файлов в индекс. Новые правки после add нужно подготовить заново. |
| Чем commit отличается от push? | `commit` сохраняет снимок локально, `push` публикует коммиты в удаленную ветку. |
| Что такое ветка? | Именованный указатель на коммит; она позволяет развивать изменения отдельно от основной линии. |
| Чем branch отличается от switch? | `branch` управляет ветками, `switch` переключает текущую. `switch -c` создает ветку и сразу переключается на нее. |
| Что делает pull? | Сначала получает удаленные изменения, затем интегрирует их. Вариант `--ff-only` отказывается объединять разошедшиеся истории автоматически. |
| Что такое merge? | Объединение историй. Возможен fast-forward либо отдельный коммит слияния. |
| Что такое конфликт? | Git не может автоматически выбрать результат несовместимых изменений. Нужно исправить файлы, проверить их, добавить в индекс и завершить слияние. |
| Что такое Pull Request? | Предложение объединить изменения ветки с целевой веткой на GitHub. В нем видны коммиты, разница файлов и обсуждение. |
| PR сам выполняет слияние? | Нет, открытие PR лишь создает предложение. Слияние — отдельное действие. |
| Зачем нужны пять коммитов? | Чтобы история отражала несколько понятных этапов работы, а не один большой несвязанный набор правок. |
| Зачем нужен .gitignore? | Чтобы случайно не добавлять окружение, кэш, секреты и временные файлы. Он не удаляет ранее сохраненные данные из истории. |
| Почему нельзя добавить только пустую папку docs? | Git отслеживает файлы; поэтому в каталоге нужна документация или другой файл. |
| Что такое origin и main? | `origin` — имя удаленного репозитория, `main` — имя ветки. Это разные сущности. |
| Что значит -u при push? | Настраивает связь локальной ветки с удаленной для дальнейших push/pull. |
| Как увидеть, что изменения действительно слиты? | Открыть PR со статусом Merged и проверить наличие файлов в main; в истории будет виден merge-коммит при выбранном способе слияния. |

## Демонстрация на защите

1. Открыть корень репозитория и показать `README.md`, `.gitignore`, `docs/`, `src/`.
2. Открыть историю коммитов и объяснить назначение каждого этапа.
3. Открыть Pull Request, показать исходную и целевую ветки, вкладку Files changed и результат слияния.
4. В локальной копии выполнить:

   ```bash
   git status
   git branch -a
   git log --oneline --graph --all
   ```

5. Открыть один из исходных скриптов и объяснить, как его запустить по README задания.
